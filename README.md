## SHA3
A small C language implementation of SHA3-256 / SHA3-512

Generated with Claude Code (https://claude.ai/code)

SHA-3 is the [Keccak](https://en.wikipedia.org/wiki/SHA-3) sponge construction standardized as [FIPS 202](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.202.pdf).

This implementation was created to provide small code to fit in a memory constrained 32 bit microcontroller.

### Why a third hash family

The other hash directories here are Merkle-Damgard: an iterated compression function with the message length appended. SHA-3 is not. It absorbs into a 1600 bit state and squeezes the digest back out, so a structural result against the Merkle-Damgard family does not carry over, and length extension does not exist to be defended against. Carrying one of each is the point; picking a favorite is not.

The Keccak constants are the other reason. Every one of them is generated by a stated rule rather than chosen: the round constants come from an 8 bit LFSR, and the rho offsets are (n+1)(n+2)/2 mod 64. There is no S-box, so there is no table in which a choice could hide. Both tables here were emitted from those rules and then compared against the published values, not transcribed.

### Why a high/low pair instead of a 64 bit type

Keccak lanes are 64 bits and C89 has neither `long long` nor `<stdint.h>`. On a machine where `unsigned long` happens to be 64 bits you could lean on it, and it is roughly two and a half times faster to do so, but the result stops building correctly on the 32 bit target this exists for. So a lane is a pair of 32 bit words and the rotate is synthesized. If your compiler does not implement "unsigned int" as 32 bits, change it in sha3256.c and sha3512.c @ typedef unsigned int sha3256_bt; to, perhaps, "unsigned long" -- the size assertion next to it will fail the build rather than let a wrong width through.

The known alternative to the plain high/low pair is bit interleaving, where a lane is held as its even and odd bits so that a 64 bit rotate becomes two 32 bit rotates. It was built and measured against this representation before being rejected: it came in under 5% faster and about 20% larger. The reason is that theta and chi are most of the work and are pure XOR, AND and NOT, which are invariant under any permutation of bit positions, so interleaving buys nothing there and only touches the rotates. That comparison harness is not in this tree. If it is ever revisited, note the measurement was taken on a 64 bit host running 32 bit typed code, which flatters neither representation honestly.

### Structure

The two digest sizes are separate translation units that each carry their own copy of the permutation, matching how rmd128 and rmd256 sit beside each other. They differ in one line, the rate. A clone can take a single .c/.h pair and build it with cc alone.

rho and pi are unrolled with literal rotate amounts on purpose. The rotate macro selects between its two arms on the amount, and that selection only folds away at compile time while the amount is a constant. Feeding offsets from a runtime table would turn each of them into a live branch.

Included are example driver programs, test/main256.c and test/main512.c, that read standard input till end-of-file and write on standard output a hex representation of the hash.

Built on the same sponge, with no dynamic allocation, are keyed primitives: HMAC ([RFC 2104](https://www.rfc-editor.org/rfc/rfc2104)) and HKDF ([RFC 5869](https://www.rfc-editor.org/rfc/rfc5869)).
HKDF feeds T(n-1) | info | counter through the hash a piece at a time rather than assembling that concatenation in a buffer, which is what lets it avoid allocation.

For SHA-3 the HMAC block is the sponge rate, not the digest size and not 128. That is 136 bytes for SHA3-256 but only 72 for SHA3-512, which is the surprise: a SHA3-512 digest is 64 bytes, so the block is barely wider than the digest it carries. `make check` covers the key-longer-than-block path for both because that is where the mistake lands.

### Testing

`make check` runs known answer tests whose expected values were produced by an independent implementation rather than by this one. Beyond the FIPS 202 spec messages it covers lengths straddling both rates -- the pad10*1 boundary, where a message ending one byte short of the rate puts the 0x06 domain tag and the 0x80 pad in the same byte -- one-shot against chunked feeding at chunk sizes that straddle both rates, and the HMAC and HKDF paths.
